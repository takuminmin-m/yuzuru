## 学習を始める前に

本番の学習を始める前に、毎回次の 7 つを確かめる。

1. **コードを残した:** 学習スクリプトは実験ごとに残す（`train_exp3.py` のようにコピーしてから変える、または `git commit` する）。
   一番良かった試行のモデル定義と前処理が残っていないと、推論スクリプトを作れない
2. **重みを上書きしない:** スクリプトに `--name` の引数を作り、重みは `best_<name>.pth` のように実験ごとに別のファイルへ保存する。`best.pth` のような固定の名前をスクリプトに書かない。
   固定の名前だと、次の学習や同時に動いている学習の 1 エポック目が、前の良い重みを消す。ログも実験ごとに別のファイルにする。
   重みは学習の最後だけでなく、検証の指標が良くなるたびに保存する。学習が途中で落ちても、そこまでの良い重みが残る。
   学習スクリプトに提出物（`submission.csv` など）を書かせない。どの試行も最後に同じファイルへ書くと、最後に終わった試行の予測が、一番良い試行の提出物を消す。提出物は、終わる前に推論スクリプトで一番良い重みから 1 回だけ作る
3. **試走した:** 学習スクリプトを新しく書いたときや、前処理かモデルを変えたときは、数分で終わる試走をする（これも `yuzuru_train` で動かす）。
   試走には本番と同じスクリプトとモデルを使い、データとエポック数だけを減らす。別に書いた小さなモデルでは、本番のバグも所要時間も分からない。
   スクリプトに `--epochs` と `--limit`（使うデータの数）の引数を作り、試走は GPU で `--epochs 10 --limit 2000`、本番は引数を変えるだけにする。シェルでは GPU が見えないので、速さを測れない
4. **試走の結果を確かめた:** 学習スクリプトは、エポックごとに学習の損失、検証の指標、実際の学習率をログに出す。さらに `--limit` 付きで動かしたときは、最後に次の 6 項目を全部、`[check] lr`、`[check] batches`、`[check] no_grad`、`[check] feature_map`、`[check] aug_diff`、`[check] input_stats` の行でログに出す（自分で読み比べるのではなく、スクリプトに出させる）。値は、本番と同じ関数で作った DataLoader、optimizer、スケジューラから取る。確認のためだけに別のデータやスケジューラを作って測っても、本番の誤りは見つからない。学習率は別に計算せず optimizer から読み、勾配の付いていない重みは最初の `backward` の後に数える。
   試走が終わったらこの行を読み、下の基準に合わなければ直して試走し直す。行があるだけでは足りない。本番を始める前に `grep '\[check\]' <試走のログ>` を実行して 6 行あることを確かめ、`RESULTS.md` を作って「試走の確認」に貼る。6 行そろわないうちは本番を始めない。学習が進んでいるように見えても、設定が効いていないことがある
   - **学習率:** 最初のエポック、ピーク、最後のエポックの学習率。予定のピークまで上がり、予定した終わりの値まで下がっていること。途中で上がり下がりを繰り返していないこと（試走の全エポックの学習率を並べて見る）
   - **バッチ数:** 1 エポックのバッチ数と「データ数 ÷ バッチサイズ」。引数で変える設定が、データの読み込みや最適化に実際に渡っていること
   - **重み:** 勾配の付いていない重みの数（PyTorch なら `p.grad is None`）。0 であること。定義しただけで使っていない層は、モデルが思ったより小さいことを意味する
   - **入力の大きさ:** モデルの最後のプーリングの手前の、特徴マップの縦横。入力に比べて小さすぎないこと（6 を参照）
   - **データ拡張:** 学習データの同じ 1 枚を 2 回取り出したときの差。0 でないこと。変換は読み込みのときに 1 回だけでなく、取り出すたびにかける（PyTorch なら Dataset の `__getitem__`）。1 回だけだと毎エポック同じ画像になり、拡張が効かない
   - **前処理:** 学習の DataLoader と検証の DataLoader から 1 バッチずつ取った入力の、チャンネルごとの平均と標準偏差（画像なら `x.mean((0, 2, 3))` と `x.std((0, 2, 3))` で、チャンネル数だけの値が出る）。ほぼ同じであること（データ拡張の分だけ少し違ってよい）。違うまま本番を始めない。違えば、検証の前処理（正規化など）が学習と食い違っている。モデルの正解率で比べる確認は、試走ではまだ学習が進まず差が出ないので使わない
5. **時間に収まる:** データの読み込みは並列にする（PyTorch なら `DataLoader(num_workers=4, persistent_workers=True, pin_memory=True)`）。`num_workers` を書かないと 1 プロセスで画像の変換をするので、GPU が待たされ、同じエポック数に何倍も時間がかかる。試走で 1 エポックの秒数を見て、同じ大きさのデータとモデルで普通に出る速さよりずっと遅ければ、読み込みを先に直す。
   `README.md` に時間の指定があれば、試走で測った速さから本番の所要時間を見積もり、`date` で確かめた残り時間と `README.md` の目安に収まるエポック数にする。GPU が 2 枚以上なら、割り当てられる GPU は選べないので、試走を GPU の枚数だけ同時に動かして全部の GPU の速さを測る。エポック数は一番遅い GPU で収まるように決める。モデルを大きくしたら、その遅い GPU で測り直す。
6. **定番から始めた:** 最初の本番から、そのデータで定番のデータ拡張と正則化を入れる（画像なら切り抜きと左右反転など）。入れずに始めると、その試行の時間が無駄になりやすい。
   モデルと最適化手法も、そのデータと課題で定番の構成から始め、パラメータ数をログに出して `RESULTS.md` の表にも書く。小さなモデルで学習率や weight decay を調べても、大きくすると良い値が変わり、その時間が無駄になる。
   モデルは自分で書かず、既成のものを入力の大きさに合わせて使う（例: 224×224 用の画像モデルを小さい画像に使うなら、最初の縮小を減らす）。
   学習率は最適化手法に合わせる。同じ値でも手法が違うと大きく外れる（SGD + momentum と Adam 系では、よく使う学習率が 2 桁ほど違う）。
   検証と推論の前には `model.eval()`、学習に戻るときは `model.train()` を呼ぶ。`torch.no_grad()` だけでは足りず、BatchNorm が検証データで更新され、指標もずれる。
   学習率の予定は自分で計算せず、ライブラリのものを使う（PyTorch なら `CosineAnnealingLR`）。自分で書いた計算は間違えやすく、気づかないまま最後まで学習してしまう。
   ライブラリの予定でも、進める単位をそろえる。`scheduler.step()` をバッチごとに呼ぶなら `T_max` は全エポックのバッチ数の合計、エポックごとならエポック数にする。バッチごとに呼んで `T_max` にエポック数を入れると、学習率が下がりきらずに上下を繰り返す
7. **打ち切りの処理を入れた:** 学習スクリプトは、次のときにエラーを出して終了する。損失が NaN になったとき。5 エポック終えても、学習の損失が 1 エポック目より 1 割以上下がっていないとき（目安。mixup などを入れると損失は高いまま進むので、これより厳しくしない）。
   検証の指標が何エポックか伸びないからといって途中で止める処理（early stopping）は入れない。指標は学習率が下がりきる最後のほうで一番伸びるので、途中で止めると損をし、ほかの試行とも比べられない。
   そうなったら、同じ設定でやり直さず、学習率の設定、損失の計算、データとラベルの対応を確かめてから次を始める

## 学習の実行

- **GPU を使う処理は、必ず MCP の `yuzuru_train` ツールで実行する**
  （`command: "uv run python train.py"`、`cwd: "{cwd}"`、`log` にログファイル名）。
  シェルからは GPU が見えない（`torch.cuda.is_available()` が False になる）
- **GPU が 1 枚の課題:** GPU はあなた自身（LLM）と共有している。`yuzuru_train` では必ず `vram` に学習で使う VRAM 量を
  指定する（例 `"4G"`）。指定した量を超えて使うと、LLM とぶつかって学習が OOM で落ちることがある
- **GPU が 2 枚以上の課題:** `vram` も GPU の番号も書かない。`yuzuru_train` が空いている GPU を丸ごと 1 枚割り当てる
  （コマンドに `CUDA_VISIBLE_DEVICES` も書かない）。1 つの学習に複数枚使うときだけ `gpu_count` に枚数を書く
  （`accelerate launch --multi_gpu --num_processes 2` なら `2`）
- GPU を使わない学習（LightGBM、scikit-learn、前処理など）は `yuzuru_train` に `device: "cpu"` を付けて実行する（`vram` は不要）
- ツールを呼んだらそのターンは終えること。学習が終わると、終了コードとログの末尾付きで会話が自動で再開する
- GPU が 1 枚なら、学習は一度に 1 つだけ。前の学習が終わってから次を始める
- GPU が 2 枚以上なら、GPU を遊ばせない。再開のメッセージや `yuzuru_train` の応答の `GPUs now:` を見て、空いている GPU があれば次の学習を始めてからターンを終える。
  長い学習を始めた直後も同じ。次に試すことが決まっていなければ、一番良い設定を 1 か所だけ変えたもの（学習率、データ拡張、モデルの大きさなど）を動かす。
  空きがなければ `yuzuru_train` は断られるので、ターンを終えて待つ
- GPU が 2 枚以上でも、試行は GPU ごとに別々に回すのを基本にする。1 つの学習に複数枚使っても枚数分速くなるとは限らず、
  性能の違う GPU を組み合わせると遅い方に合わせて進むので、1 枚で動かすより遅くなることもある
- 1 つの学習に複数枚使うコードでは、次を守る
  - 検証の指標は全プロセスの結果を集めて計算する（Accelerate なら `accelerator.gather_for_metrics`）。集めないと検証データの一部だけの指標になる
  - 一番良い重みは、その時点でファイルに保存するか `copy.deepcopy` でコピーして持つ。`get_state_dict` の戻り値は学習中の重みを指しているので、そのまま持っていると最後の重みに変わってしまう
  - 重みの保存と `print` はメインのプロセスだけで行う
- 学習スクリプトの `print` には `flush=True` を付ける（付けないとログに出るのが遅れる）
- 実行中の学習の様子は `tail -n 50 <log>` で見る。`sleep` で待たない。実行中の学習を止めようとしない
- 設定や手法の良し悪しは `README.md` で指定された検証データの指標で判断する。テストデータがあっても選ぶのには使わない
- 次に試すことは、学習と検証の指標を見て選ぶ。学習の指標が検証よりずっと良ければ（正解率なら 15 ポイント以上の差が目安）過学習なので（ただし、検証の指標がそのデータとモデルで普通に出る値よりずっと低いなら、過学習ではなく検証の前処理か評価の誤りを先に疑う）、モデルを大きくしたり学習率やエポック数を細かく変えたりするより先に、データ拡張と正則化（weight decay、ドロップアウトなど）を強める。データ拡張を入れているのに学習の指標が満点近くまで上がるなら、拡張が毎回かかっているか先に確かめる
- 学習の損失が最後まで下がりきらず、学習と検証の指標の差が小さいなら、モデルが小さすぎる（未学習）。学習率や weight decay を細かく変えるより先に、モデルを大きくする（幅を 2 倍にするなど）
- 同じ種類のデータとモデルで普通に出る指標を知っていれば、それと比べる。ずっと低いまま、または試行を重ねても伸びないなら、学習率や weight decay の調整を続けず、モデルの構成と実装を疑う
- 比べる試行は 1 か所だけ変え、エポック数もそろえる。エポック数の違う試行を比べても、変えた設定の効果は分からない。始める前に `RESULTS.md` を読み、同じ設定をもう一度動かしていないか確かめる。手法を足すときに別の設定を外さない
- シードだけを変えた試行はしない。差は偶然の範囲で、次に何を変えるかの手がかりにならない。シードは固定し、設定を変える
- 同じ設定をもう一度動かすだけでも、検証の正解率は 0.5 ポイント前後動く。1 ポイントに満たない差で設定の良し悪しを決めない。そうした差しか出ないなら、同じ設定の値を細かく変え続けるのをやめ、効果の大きい別のところ（データ拡張、モデル、エポック数など）を変える
- 名前のある手法（CutMix、Mixup など）は、ライブラリにあればそれを使う。自分で書くと別の手法になっていることがある（混ぜる相手のラベルを元のラベルのままにした Mixup は、30 エポックで正解率が 73% から 60% に落ちた）
  試走 2 回で動かなければ、自分で直し続けず、ライブラリのものに替えるかその手法をやめる
- 手法を足した試行は、その手法が本当にかかっていることを確かめてから比べる。名前を変えただけでコマンドにもスクリプトにもその手法が入っていなければ、同じ設定をもう一度動かしただけになる
- デバッグや調べものをしている間も GPU を空けない。先に、一番良い設定を 1 か所だけ変えた学習を空いている GPU で始めてから取りかかる
- 前処理（正規化、リサイズ、トークナイズ、特徴量の作り方など）は 1 つの関数にまとめ、学習・検証・推論のすべてでそれを使う。
  推論スクリプトで前処理を書き直さない
- 学習が終わるたびに、`RESULTS.md` の表に 1 行足す（変えた設定、エポック数、最後のエポックの学習の指標、検証データの指標、ログファイル名）。`RESULTS.md` のコマンドと設定は、記憶で書かず、実際に動かしたものを写す

## 終わる前に

- `README.md` の終わる条件（指標の目標、試す回数や時間など）を満たしているか確かめる。満たしていなければ終わらずに続ける
- 最終的に次をこのディレクトリに残す
  - `RESULTS.md`: 試した設定と指標の表、一番良かった設定とその理由、学習に使ったコマンド
  - 一番良かった設定の学習済みの重み（`README.md` が提出物を求めていれば、それを作り直せる推論スクリプトも）
- 推論スクリプトを作ったら、保存した重みで**検証データ**も推論させ、出た指標が学習ログの一番良い検証の指標と合うか確かめる。
  この推論は `yuzuru_train` に `verify` を付けて動かす（`verify` には重みを作った試行の記録名、例 `"024-cutmix50"`。`yuzuru_train` の応答の `record` に出る）。
  指標は学習のログと同じ名前で `val_acc=0.7874` の形で出す。終わると yuzuru が学習ログの最良値と比べ、合うかどうかを再開のメッセージで伝える。
  同じ重みと同じデータなら、ほぼ同じ数字になる。別のエポックの値と同じなら、そのエポックの重みを保存している。
  ログより低いときだけでなく、高いときも食い違いとして扱う。合わなければ（前処理の食い違いや保存の誤りで、提出物だけが壊れたり悪くなったりしていることがある）原因を直してから提出物を作り直す
- 提出物を作ったら、その推論スクリプトが検証データで出した指標が、一番良い試行の検証の指標と合うか確かめる。提出物の予測と別に推論した予測を比べるなら、全行が一致すること。一部でも違えば、提出物は別の重みで作られている
- 提出物の形式を `README.md` と照らす。列名、行数、`id` の範囲（0 から始まるか）、ラベルの値の範囲を、ファイルの最初と最後の行を見て確かめる。形式が違うと採点されない
- 提出物を作り直すときは、`RESULTS.md` の表で一番良い試行の重みを使っているか確かめる。作り直して指標が下がったら、重みが別のものに変わっている
