## 学習を始める前に

本番の学習を始める前に、毎回次の 7 つを確かめる。

1. **コードを残した:** 学習スクリプトは実験ごとに残す（`train_exp3.py` のようにコピーしてから変える、または `git commit` する）。
   一番良かった試行のモデル定義と前処理が残っていないと、推論スクリプトを作れない
2. **重みを上書きしない:** 重みとログは課題のディレクトリの中に、実験ごとに別のファイル名で保存する。前の良い重みを消さない。
   重みは学習の最後だけでなく、検証の指標が良くなるたびに保存する。学習は時間の上限で止められることがある
3. **試走した:** 学習スクリプトを新しく書いたときや、前処理かモデルを変えたときは、数分で終わる試走をする（これも `yuzuru_train` で動かす）。
   試走には本番と同じスクリプトとモデルを使い、データとエポック数だけを減らす。別に書いた小さなモデルでは、本番のバグも所要時間も分からない。
   スクリプトに `--epochs` と `--limit`（使うデータの数）の引数を作り、試走は GPU で `--epochs 10 --limit 2000`、本番は引数を変えるだけにする。シェルでは GPU が見えないので、速さを測れない
4. **試走の結果を確かめた:** 学習スクリプトは、エポックごとに学習の損失、検証の指標、実際の学習率をログに出す。さらに `--limit` 付きで動かしたときは、最後に次の 6 つの数字を全部、`[check]` で始まる行でログに出す（自分で読み比べるのではなく、スクリプトに出させる）。
   試走が終わったらこの行を読み、おかしければ直して試走し直す。`[check]` の行は `RESULTS.md` の「試走の確認」に貼る。学習が進んでいるように見えても、設定が効いていないことがある
   - **学習率:** 最初のエポック、ピーク、最後のエポックの学習率。予定のピークまで上がり、予定した終わりの値まで下がっていること
   - **バッチ数:** 1 エポックのバッチ数と「データ数 ÷ バッチサイズ」。引数で変える設定が、データの読み込みや最適化に実際に渡っていること
   - **重み:** 勾配の付いていない重みの数（PyTorch なら `p.grad is None`）。0 であること。定義しただけで使っていない層は、モデルが思ったより小さいことを意味する
   - **入力の大きさ:** モデルの最後のプーリングの手前の、特徴マップの縦横。入力に比べて小さすぎないこと（6 を参照）
   - **データ拡張:** 学習データの同じ 1 枚を 2 回取り出したときの差。0 でないこと。変換は読み込みのときに 1 回だけでなく、取り出すたびにかける（PyTorch なら Dataset の `__getitem__`）。1 回だけだと毎エポック同じ画像になり、拡張が効かない
   - **前処理:** 学習データの一部を検証と同じ処理で評価した指標と、学習中の指標。大きく低ければ、検証の前処理が学習と食い違っている
5. **時間に収まる:** `README.md` に時間の指定があれば、試走で測った速さから本番の所要時間を見積もり、`date` で確かめた残り時間と `README.md` の目安に収まるエポック数にする。GPU が 2 枚以上なら、遅い方の GPU とモデルの大きさも考えて見積もる。
   時間の上限で止められた学習は、学習率が下がりきらず、ほかの試行と比べられない。止められたら、同じエポック数で次を始めず、収まるように減らす
6. **定番から始めた:** 最初の本番から、そのデータで定番のデータ拡張と正則化を入れる（画像なら切り抜きと左右反転など）。入れずに始めると、その試行の時間が無駄になりやすい。
   既成のモデルは、想定の入力サイズに合わせて使う。たとえば torchvision の ResNet は 224×224 用で、32×32 の画像はプーリングの前に 8×8 まで縮み、情報を失う。小さい画像なら、最初の畳み込みを 3×3・ストライド 1 にして最初のプーリングを外す。
   学習率の予定は自分で計算せず、ライブラリのものを使う（PyTorch なら `CosineAnnealingLR`）。自分で書いた計算は間違えやすく、気づかないまま最後まで学習してしまう
7. **打ち切りの処理を入れた:** 学習スクリプトは、次のときにエラーを出して終了する。損失が NaN になったとき。5 エポック終えても、学習の損失が 1 エポック目より 1 割以上下がっていないとき（目安）。
   そうなったら、同じ設定でやり直さず、学習率の設定、損失の計算、データとラベルの対応を確かめてから次を始める

## 学習の実行

- **GPU を使う処理は、必ず MCP の `yuzuru_train` ツールで実行する**
  （`command: "uv run python train.py"`、`cwd: "{cwd}"`、`log` にログファイル名）。
  シェルからは GPU が見えない（`torch.cuda.is_available()` が False になる）
- **GPU が 1 枚の課題:** GPU はあなた自身（LLM）と共有している。`yuzuru_train` では必ず `vram` に学習で使う VRAM 量を
  指定する（例 `"4G"`）。指定した量を超えて使うと、LLM とぶつかって学習が OOM で落ちることがある
- **GPU が 2 枚以上の課題:** `vram` も GPU の番号も書かない。`yuzuru_train` が空いている GPU を丸ごと 1 枚割り当てる
  （コマンドに `CUDA_VISIBLE_DEVICES` も書かない）。1 つの学習に複数枚使うときだけ `gpu_count` に枚数を書く
  （`accelerate launch --multi_gpu --num_processes 2` なら `2`）
- GPU を使わない学習（LightGBM、scikit-learn、前処理など）は `yuzuru_train` に `device: "cpu"` を付けて実行する（`vram` は不要）
- ツールを呼んだらそのターンは終えること。学習が終わると、終了コードとログの末尾付きで会話が自動で再開する
- GPU が 1 枚なら、学習は一度に 1 つだけ。前の学習が終わってから次を始める
- GPU が 2 枚以上なら、GPU を遊ばせない。再開のメッセージや `yuzuru_train` の応答の `GPUs now:` を見て、空いている GPU があれば次の学習を始めてからターンを終える。
  長い学習を始めた直後も同じ。次に試すことが決まっていなければ、一番良い設定を 1 か所だけ変えたもの（学習率、データ拡張、モデルの大きさなど）を動かす。
  空きがなければ `yuzuru_train` は断られるので、ターンを終えて待つ
- GPU が 2 枚以上でも、試行は GPU ごとに別々に回すのを基本にする。1 つの学習に複数枚使っても枚数分速くなるとは限らず、
  性能の違う GPU を組み合わせると遅い方に合わせて進むので、1 枚で動かすより遅くなることもある
- 1 つの学習に複数枚使うコードでは、次を守る
  - 検証の指標は全プロセスの結果を集めて計算する（Accelerate なら `accelerator.gather_for_metrics`）。集めないと検証データの一部だけの指標になる
  - 一番良い重みは、その時点でファイルに保存するか `copy.deepcopy` でコピーして持つ。`get_state_dict` の戻り値は学習中の重みを指しているので、そのまま持っていると最後の重みに変わってしまう
  - 重みの保存と `print` はメインのプロセスだけで行う
- 学習スクリプトの `print` には `flush=True` を付ける（付けないとログに出るのが遅れる）
- 実行中の学習の様子は `tail -n 50 <log>` で見る。`sleep` で待たない。実行中の学習を止めようとしない
- 設定や手法の良し悪しは `README.md` で指定された検証データの指標で判断する。テストデータがあっても選ぶのには使わない
- 次に試すことは、学習と検証の指標を見て選ぶ。学習の指標が検証よりずっと良ければ過学習なので、学習率やエポック数を細かく変えるより、データ拡張、正則化（ドロップアウト、weight decay など）、モデルの構成を変える。データ拡張を入れているのに学習の指標が満点近くまで上がるなら、拡張が毎回かかっているか先に確かめる
- 同じ種類のデータとモデルで普通に出る指標を知っていれば、それと比べる。ずっと低いまま、または試行を重ねても伸びないなら、学習率や weight decay の調整を続けず、モデルの構成と実装を疑う
- 比べる試行は 1 か所だけ変える。始める前に `RESULTS.md` を読み、同じ設定をもう一度動かしていないか確かめる
- 前処理（正規化、リサイズ、トークナイズ、特徴量の作り方など）は 1 つの関数にまとめ、学習・検証・推論のすべてでそれを使う。
  推論スクリプトで前処理を書き直さない
- 学習が終わるたびに、`RESULTS.md` の表に 1 行足す（変えた設定、検証データの指標、ログファイル名）。`RESULTS.md` のコマンドと設定は、記憶で書かず、実際に動かしたものを写す

## 終わる前に

- `README.md` の終わる条件（指標の目標、試す回数や時間など）を満たしているか確かめる。満たしていなければ終わらずに続ける
- 最終的に次をこのディレクトリに残す
  - `RESULTS.md`: 試した設定と指標の表、一番良かった設定とその理由、学習に使ったコマンド
  - 一番良かった設定の学習済みの重み（`README.md` が提出物を求めていれば、それを作り直せる推論スクリプトも）
- 推論スクリプトを作ったら、保存した重みで**検証データ**も推論させ、出た指標が学習ログの検証の指標と合うか確かめる。
  合わなければ（前処理の食い違いなどで、提出物だけが壊れていることがある）原因を直してから提出物を作り直す
